# Contributing

## Workflow
1. Pick an issue. Create a branch named `type/<issue-number>-short-name`, for example `feat/12-quaternion-utilities`.
2. Write a test for the first acceptance criterion, make it pass, and repeat for the rest.
3. Run the local checks (see README, "Development") and fix anything they report.
4. Commit with a message of the form `type(scope): summary`, for example `feat(math): add quaternion utilities`.
5. Open a pull request titled like the issue, with `Closes #<issue-number>` in the description. Wait for CI to pass, then squash-merge.

## Types
`feat`, `fix`, `test`, `docs`, `build`, `ci`, `perf`, `refactor`, `chore`, `spike`.

## Standards
- Every behavior change has a test. Every number quoted in the README can be regenerated by a command.
- Formatting and linting are enforced by CI; run the formatter instead of editing style by hand.
- Every file carries licensing information, either an SPDX header or coverage by `REUSE.toml`; `reuse lint` must pass.
- Releases are tagged `vMAJOR.MINOR.PATCH`.
